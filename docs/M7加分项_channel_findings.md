# 加分项① 问题发现：真实信道对"可恢复性"与"内容加密"的破坏（exp8）

> 实验：`experiments/exp8_channel_cases.py`（2026-11-02 跑完）
> 数据：LibriSpeech test-clean，A1=10 人×5 句（声学线）、A2=50 句/122 敏感词（内容线，与 M4 eval_fnr 同采样法）
> 协议：single 模式 dist∈(0.5,0.6) n∈[1,10]、margin=8 帧、评估 ASR=Conformer beam=4、ASV=ECAPA 余弦
> 结果文件：`experiments/results/exp8_cases.json` + `exp8_hyp_cache.json`；试听样例 `data/probe/exp8/`
> 信道：mp3_128k/64k（微信语音重编码代理，计划允许）、resample_8k（电话带宽）、noise_10db、
> rerecord（合成 IR+带通+底噪翻录仿真）、trim_400ms（VAD 掐头，微信语音裁静音行为）

## 1. A1 声学恢复链：protect → 信道 → 持密钥 recover

| 信道 | 恢复后 WER% | 攻击者可懂度 WER%（protect 后未恢复） | 说话人相似度 sim（recover 后 vs 原始） |
|---|---|---|---|
| clean（基线） | **1.99** | 5.10 | **0.904** |
| mp3_128k | 1.90 | 5.36 | 0.902 |
| mp3_64k | 1.99 | 5.10 | 0.900 |
| resample_8k | 2.08 | 12.63 | **0.657** |
| noise_10db | 4.67 | 22.75 | **0.684** |
| rerecord | 3.72 | 20.59 | **0.663** |
| trim_400ms | 3.98 | 6.49 | 0.850 |

（sanity：clean 行 WER 1.99% 与 M3 全集恢复 WER 2.23%、protected 5.1% 与 M3 保护后 5.44% 同量级 ✓；
无信道 sim(protected)=0.276 说明匿名化本身正常。）

### 发现 F1：内容可懂度全信道稳健，**声纹恢复才是脆弱面**
所有信道下恢复后 WER 都 ≤4.7%（内容完好），但 8k 带宽/噪声/翻录三道的说话人相似度从 0.90 掉到 0.66——
**逆 warping 只能抵消 warping，抵消不了信道自身对声纹高频细节的破坏**（不可逆损伤叠加在可逆扰动之后）。
"可恢复"在真实信道下的准确表述是：**内容可恢复、声纹部分可恢复**。

### 发现 F2：MP3 重编码（≥64kbps）几乎无害，8k 重采样才是杀手
mp3_64k 的 sim=0.900 与 clean 无异——128/64kbps MP3 的量化噪声底在 16k 语音的声纹线索之下；
而 8k 往返直接抹掉 4kHz 以上全部声纹信息（sim 0.657）。**带宽是主因、码率是次因**——
这修正了"微信语音=低码率所以危险"的直觉。

### 发现 F3（机理预告）：single 模式对全局时移天然免疫
trim_400ms 下 sim 仍有 0.85、WER 3.98%——因为 single 模式整句共用**同一个**频率映射，
内容平移后逐帧逆映射依然逐帧正确，损失只来自被裁掉的 400ms 头部。
**推论**：若用逐段映射（ola/block 模式），时移会让"帧位置↔映射段"错配，恢复应显著崩坏——
③机理分析里用对照实验验证这个预测，反证 M3 选择 single 模式的额外鲁棒性收益。

## 2. A2 内容加密链：encrypt → 信道 → 按原帧号 decrypt

| 信道 | FNR（decrypt 后敏感词仍隐藏率） | 解读 |
|---|---|---|
| clean | **10.0%**（幸存 108/120） | 解密成功→管理员听到原文——**这正是 Dec 态应有行为**（对照 M4 Ori FNR 8.57% ✓） |
| mp3_128k / 64k | 96.7% | 密文被重编码打乱 → 按原密钥解密得到乱码 → **连管理员都恢复不出内容** |
| resample_8k | 97.5% | 同上 |
| noise / rerecord / trim | 98.3% | 同上 |

### 发现 F4："加密区间渗漏"假说被证伪，真正的失效是**可用性**
原计划假设"帧边界错位会让敏感词边缘渗漏"。实测相反：**密文随内容整体平移/重编码，
平移不会把密文变回明文**——隐私面在所有信道下都成立（攻击者视角 nod 抽查亦无泄漏，
与 M4 eval_fnr_mp3 的 enc=100% 一致）。但代价反转：任何有损信道之后，
**持密钥的合法方也解不回原文**（FNR 从 10% 跳到 96.7%+）——
AES-CTR 字节级加密对"信道必须字节级保真"的隐含假设不成立。
论文场景里这意味着：经微信转发的加密语音，管理员拿回的是乱码而非原文。

### 发现 F5：时移信道的附带损伤
trim_400ms 下解密区间与密文错位——解密 XOR 落在**明文**上，把区间内无辜内容变成噪声
（附带损伤），敏感词反而因仍在密文区而安全。drift 测量（rerecord/trim 互相关失锁=nan）
佐证帧网格语义已被信道摧毁。

## 4. ②控制变量扫描结论（exp9 完成，`exp9_sweep.json` + `fig_exp9_curves.png`）

每维固定其余条件扫 3-4 点，四条曲线（recovered-WER / recovered-EER / sim / A2-FNR）：

| 维度 | 扫描点 | recovered WER% | recovered EER% | sim | A2-FNR% |
|---|---|---|---|---|---|
| MP3 码率 | 32/64/128/192k | 2.08/1.99/1.90/1.99 | 0/0/0/0 | .81/.90/.90/.90 | 97.5/97.5/96.7/96.7 |
| 噪声 SNR | 0/5/10/20dB | **50.5/14.8/5.0/2.0** | **8.0/3.3/2.4/0.1** | .50/.60/.69/.80 | 100/100/97.5/**88.3** |
| 带宽 | 8/11.025/22.05k | 2.08/2.16/1.99 | 3.0/0/0 | .66/.76/.90 | 97.5/96.7/96.7 |

### 发现 F6：噪声是三维中最危险的轴，且**双向恶化**
SNR 从 20dB 降到 0dB：恢复端 WER 2.0→50.5%（管理员拿不回内容）、EER 0.1→8.0%（声纹恢复劣化）
——单调曲线族成立，问题普遍存在非偶发（②的验收点）。

### 发现 F7（关键新路径）：轻微噪声下加密区间**真的会渗漏**，机理是字节微扰动不是时移
FNR 随 SNR **升高**反而下降：20dB 时 88.3%（14/120 敏感词被 ASR 认出），0/5dB 反而 100%。
机理：AES-CTR 是流密码且**无完整性校验**——小幅扰动（高 SNR 噪声只改变少量 int16 字节）
经解密 XOR 后大部分明文被原样还原，只有受扰字节出错 → 敏感词以"带瑕疵的明文"形态泄漏；
大扰动（低 SNR）反而把整段打成乱码 → 无泄漏但管理员也解不开（F4 的可用性失效）。
**"渗漏需要字节级微扰、崩坏源于字节级剧扰"**——同一机制的两端，一张图讲完。
（对照 exp8：时移/重编码类信道全部 FNR≥96.7%，证实 F4 的"平移不渗漏"结论。）

### 发现 F8：MP3 码率维度近乎免疫（32k 才开始伤声纹）
WER/EER 全码率平坦；sim 仅 32kbps 掉到 0.81。结合 F2：**对微信类转发（64k 语音），
声纹/内容恢复几乎无损；风险集中在电话带宽（8k）与噪声**。

### 对 ④改进的指向（更新）
- 渗漏路径（F7）→ 加密对象加**完整性标签**（每 span 存 4 字节校验/哈希于密钥包），
  解密校验失败即拒绝输出明文、回退静音——把"部分渗漏"变成"干净失败"；
- 时移路径（F5 附带损伤）→ 恢复端同步锚点预对齐（exp10-C）；
- 声纹恢复（F1/F6）→ 恢复端谱减均衡（exp10-C 对照）。

## 5. ③机理分析（exp10 A/B 完成，`exp10_mechanism_improve.json`）

### M1 时移错配矩阵——F3 推论证实，single 模式的隐藏优势
同一批 50 句、同一随机种子，warping 模式 × trim_400ms：

| 模式 | clean WER% | trim WER% | clean sim | trim sim |
|---|---|---|---|---|
| **single（本系统默认）** | 1.90 | **3.55** | 0.940 | **0.899** |
| ola（逐段映射+加窗合成） | 1.90 | **36.16** | 0.899 | 0.516 |
| block（逐段映射+矩形块） | 2.08 | **56.40** | 0.880 | 0.462 |

机理：时移 k 帧后，第 i 帧收到的内容本应属于第 i-k 帧的映射。
single 全句一个映射 → 逆映射对任何帧都正确（免疫）；
ola/block 逐段独立映射 → "帧位置↔参数段"错配 → 逆扭曲作用在错误内容上，
WER 爆炸（36-56%）且声纹恢复崩坏（sim 0.46-0.52）。
**结论：M3 为复现论文工作点选的 single 模式，附带获得了"对全局时移免疫"的信道鲁棒性——
这是论文未讨论的实现层发现，也解释了 F4 中 trim 几乎不破坏声学恢复的原因。**

### M2 频带证据——F1/F2 的"为什么"（recover 后 vs 原始，10 句平均）
| 信道 | 0-2k 谱相关 | 2-4k | 4-8k | 4-8k 能量差 |
|---|---|---|---|---|
| mp3_128k/64k | 0.973 | 0.71 | **0.80-0.81** | -4.9dB |
| resample_8k | 0.973 | 0.47 | **0.093** | **-60.2dB** |
| noise_10db | 0.963 | 0.28 | **0.159** | +6.6dB（噪声能量灌入） |
| rerecord | 0.716 | 0.54 | 0.61 | -4.2dB（IR 拖尾全带抹糊） |

- 8k 信道把 4-8k 带**物理清零**（-60dB、相关 0.09）、2-4k 带相关也只剩 0.47，
  而 0-2k 带完好（0.973）——sim 却仍掉到 0.657：说明 ECAPA 声纹可分性中相当一部分
  信息承载于 2-8kHz，被带宽信道不可逆抹除（F2）；
- 噪声在高带**灌入能量**（+6.6dB、相关 0.16）——信噪比恶化掩盖 warping 后的高频特征（F1/F6）；
- mp3 的感知编码把 4-8k 带相关度保持在 0.80 → 码率维度近乎无害（F8）。
**三张表合起来：声纹恢复的退化量 = 信道对 2-8kHz 带的破坏量。**

## 6. ④改进方案与验证（exp10-C/D + exp11，全部完成）

### I1 同步锚点预对齐（exp10-C）——诚实的弱结果，反证 M1
同种子配对对照（未对齐 → 预对齐后恢复）：

| 信道 | WER naive → aligned | sim naive → aligned |
|---|---|---|
| trim_400ms | 3.55 → 3.29 | 0.899 → 0.913 |
| noise_10db | 4.84 → 5.80 | 0.720 → 0.723 |
| rerecord | 4.33 → 5.02 | 0.696 → 0.695 |
| resample_8k | 2.34 → 2.25 | 0.636 → 0.637 |

解读：预对齐只在 trim 上有可见收益（且本来就小），噪声/翻录信道下 VAD 首有声帧锚点
被噪声干扰、对齐反噬（WER +0.7~1.0pp）。**结论：single 模式（M1）已经消化了时移问题，
"先均衡再恢复"没有额外空间——改进重心应放在内容侧（I2/I3），这组负结果本身就是论证。**

### I2 quiet 分发版 = "时间级恢复"的可用性兜底（exp10-D + exp11-E 复测）
二次转码（128k→64k）后：窗外谱相关 0.976-0.992（无辜内容完好）；
窗内 RMS 首测有 -24.8dB 离群值——归因为**双重转码的编解码延迟让窗边界错位 ~100ms**
（F5 的又一次现身）；exp11-E 排除边界 ±100ms 只测窗核心：**6/6 句全部 -240dBFS
（纯数字零）**——quiet 版的敏感窗静音在二次转码后完全保持，坐实其信道鲁棒交付形态。
定性结论：quiet 版不依赖字节保真，信道只能"再抹一点"不能"恢复出"——
**内容可用性的正确交付形态是"quiet 公开版 + 密钥旁路原文"，而非"密文版直发"**。

### I3 加密对象完整性标签 MAC（exp11）——主改进，验证成功
机制：publish 端每加密对象存 `SHA256(明文帧体)[:4]` 于密钥包；解密端校验失败
→ 该区间回退静音。把"字节微扰→部分明文渗漏"变成"字节微扰→干净失败"。
同种子配对对照（50 句/120 敏感词，Conformer beam=4）：

| 信道 | naive FNR | MAC FNR | 泄漏词数 |
|---|---|---|---|
| clean | 0.092 | **0.092（不变）** | 109→109（合法解密完全不受影响） |
| noise_20db | 0.883 | **0.983** | 14→2 |
| noise_10db | 0.975 | **1.000** | 3→0 |

**结论：MAC 把 F7 渗漏路径基本封死（20dB 噪声下泄漏面 11.7%→1.7%，剩余 2 词为
上下文脑补幸存，同 M4 幸存分析），而 clean 信道下管理员解密零代价（FNR 分毫不动）。
对照组叙事完整："原方法在信道 C（轻噪声转发）下渗漏 → 改进方法在 C 下恢复干净失败"。**

**踩坑记录（工程诚实，报告可用）**：exp11 v1 首跑时 clean 的 MAC FNR 也变成 0.983
（合法解密被全拒）——根因是 float↔int16 往返用 `/32768` 正向、`*32767` 逆向 + 截断，
"clean 信道"本身就有 1-LSB 字节扰动；naive 解密对 LSB 不敏感（音频仍可懂），
严格字节哈希 MAC 却因此拒掉一切。修复=逆向改 `round(×32768)` 并加逐字节自检断言
（v2 实测 50/50 句 clean 往返逐字节精确）。这个 bug 本身就是 F7 机理的活教材：
**字节级保真假设必须显式声明并校验，否则"隐私"与"可用性"会互相掩盖**。
